MCP 发布无状态新规范，为史上最大一次改动

MCP 2026-07-28 版规范正式定稿，取消协议层会话，用自包含请求替代 initialize 握手流程。

模型上下文协议（MCP）于 7 月 28 日正式发布 2026-07-28 版规范的稳定版，这是该标准自 2024 年底问世以来幅度最大的一次架构调整。核心变化只有一句话：MCP 在协议层不再是有状态的。

改了什么

initialize/initialized 握手流程和 Mcp-Session-Id 请求头双双退场。协议版本、客户端身份、能力声明等信息，现在由每个请求自己通过 _meta 字段携带。这意味着服务端集群可以直接挂在普通负载均衡后面，任意实例都能处理任意请求，不再需要共享会话存储。

去掉常驻连接后，服务端主动发起请求的能力需要新的承载方式。规范为此引入 Multi Round-Trip Requests：当工具执行到一半需要用户补充信息时，服务端返回类型为 input_required 的结果并附上待确认项，客户端再带着 inputResponses 重新发起调用。请求还新增了 Mcp-Method 和 Mcp-Name 两个 HTTP 头，网关和限流组件不必解析 JSON 请求体即可完成路由与计量；四个 list 方法以及 resources/read 则开始返回 ttlMs 和 cacheScope 缓存提示。

鉴权部分同步收紧：加入 RFC 9207 签发方校验，客户端凭据与签发它的授权服务器绑定，动态客户端注册（DCR）被正式标记为废弃，改为推荐 Client ID Metadata Documents。Tasks 从实验性核心毕业，成为独立扩展 io.modelcontextprotocol/tasks。Roots、Sampling、Logging 以及旧版 HTTP+SSE 传输全部进入废弃流程，官方承诺至少保留十二个月过渡期。

发布同时，TypeScript、Python、Go、C# 四个一级 SDK 已支持新版本，Rust SDK 处于 beta。候选版早在 5 月 21 日就已冻结，给实现方留出了约十周时间用真实流量做验证。

为什么重要

MCP 已是模型接入外部工具的事实标准，官方称其 SDK 月下载量接近五亿次。传输层转向无状态，抹掉了大规模部署 MCP 服务端最主要的运维障碍——会话粘连，也让这套协议从“主要跑在本地”真正变成可以按普通 Web 服务方式部署的东西。代价是所有现存服务端和客户端都要经历一次真正的破坏性迁移，摊在一年的废弃窗口里完成。
