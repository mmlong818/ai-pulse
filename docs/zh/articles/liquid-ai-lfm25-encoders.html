Liquid AI 开源两款 8K 上下文 CPU 编码器模型

LFM2.5-Encoder-230M 与 350M 由该公司解码器改造而来，称在 CPU 上处理 8K 文本比 ModernBERT-base 快约三倍。

Liquid AI 开源了两款小型双向编码器模型——LFM2.5-Encoder-230M 和 LFM2.5-Encoder-350M，上下文窗口均为 8192 token，权重已上线 Hugging Face。

模型本身

Liquid 没有从零训练编码器，而是改造了已有的 LFM2.5 解码器 checkpoint。做法是启用双向注意力掩码，把因果短卷积换成非因果版本，再以 30% 掩码率作为掩码语言模型继续训练。产出是一对覆盖 15 种语言的通用底座编码器，定位是让使用者自行微调出分类、token 分类、检索、重排、语义相似度等任务专用模型——这些恰恰是生成式模型抢走注意力和预算之后，仍在支撑生产环境 NLP 的活儿。

230M 版面向对延迟和内存吃紧的场景，350M 版则主打下游效果上限。Liquid 重点强调的是通用硬件上的长文本吞吐：在 CPU 上处理 8K token 时，230M 模型完成一次前向传播约需 28 秒，而 ModernBERT-base 需要 90 秒以上。官方称模型在自然语言推理、复述检测、情感分析及多语言评测上均有竞争力。

为什么重要

编码器是已部署 AI 体系里那层不起眼但真正承重的结构。检索管道、重排器、内容分类器、安全过滤器的请求量远高于它们服务的生成模型，而且延迟预算以毫秒计。BERT 系架构能占住这个位置多年，很大程度上是因为一直没有出现「更小更快、质量相当、上下文够用」的替代品。

Liquid 瞄准的具体缺口是「无 GPU 的长文本推理」。今天多数检索与分类栈要么在 512 token 处激进截断，要么为此采购本不必要的加速卡。一个在 CPU 上处理 8K 仍然可用的编码器，会改变端侧部署以及大量在普通服务器上跑文档分类的中小企业的成本结构。这是一次范围很窄、没有前沿级噱头的发布——也正因如此，它往往会悄悄进入相当多已上线的基础设施。
